掌柜智库项目 Day 10｜RRF 融合、Reranker 重排与结果处理

发表于2026-09-30|更新于2026-10-16|开发掌柜智库项目
|总字数:1.9k|阅读时长:7分钟|浏览量:

用权重加 RRF 思路精炼两路向量检索结果，再引入 bge-reranker-large 对多源候选统一打分与动态 TopK 截取，最后通过 output_answer 节点生成答案并正则提取图片地址。

本篇要点

  • node_rrf 节点：用“权重 + RRF”把两路向量检索结果再次精炼
  • reranker 节点：面向多源候选统一打分与动态截取
  • MTEB 模型对比、bge-reranker-large 加载与 compute_score 打分
  • token 长度计算与重排序模型上下文超长处理
  • output_answer 节点：流式 / 非流式返回、正则提取 image_urls、保存聊天记录

内容回顾

1、检索节点

  • node_search_embedding：rewritten_query 的向量与 chunks 的 content（item_name + title + content）做混合 + 条件检索，生成 embedding_chunks。
  • node_search_embedding_hyde：先用大模型基于原问题生成假设性标准回答，再用“问题 + 答案”的向量复用混合检索链路，生成第二路增强召回 hyde_embedding_chunks。
  • node_web_search_mcp：通过 MCP 调用百炼联网搜索工具补全数据，生成 web_search_docs。

2、节点参数取向

  • 数据库内检索两路都带 expr="item_name in [item_names]" 的 item_name 前置过滤。

注意： 问题和建设性问题检索，包装的数据类型 key 用 chunk_id，评估代码也依赖 chunk_id。

  • 使用：embedding_chunks、hyde_embedding_chunks。
  • 生成：rrf_chunks。

  3. 使用 RRF 算法进行数据处理（list）→ rrf_chunks[5]。

  5. 返回 state。

2、reranker 节点

作用： 对 rrf_chunks 粗排序的结果 + 非数据库中 mcp 网络搜索的结果进行最终打分 + 动态截取，产出最终候选者。

为什么在这里需要 reranker 模型？ 因为这两路数据没有统一的排名参照物！Reranker 的职责就是：reranker -> 打分 -> 算法截取 -> 最终的候选者。

参数：

  • 使用：rrf_chunks、web_search_docs、rewritten_query。
  • 生成：reranked_docs。

2.2 为什么使用 bge-reranker-large

选择 bge-reranker-large 的三个理由：

  1. 适配语言（多语言支持友好）。
  2. 性能的问题（重排效果更好）。
  3. milvus 兼容——与 bge-m3 配套使用。

重排序模型的输入是 [问题, 答案] 这样的一对：

打分时的格式是：\s问题\s \s答案\s。

面试题：重排序模型的上下文可能短于 content 内容，你是如何处理的？

  1. 换模型 → 需要重新评估。

  2. 压缩比较内容：把 content 用 LLM 压缩后再比较打分（选择该方案）。

  3. 冷处理 → 不管。

2.8 业务步骤

  1. 获取并且校验参数（state） → rewritten_query、rrf_chunks、web_search_docs。

  2. 数据格式化处理：把两类数据统一成一种格式再交给模型。

    字段对齐关系：

    rrf_chunks web_search_docs 统一字段 说明
    chunk_id 没有 chunk_id 数据库里才有的标识
    content snippt text 回答参考内容
    title title title 标题
    score 没有 score web 记 0；milvus 记 rrf 的分，之后由 reranker 打分
    type 没有 type mcp 记 web；数据库记 milvus
    url 没用 url 图片地址

    最终得到 reranker_list。

  3. 组装问题和答案的列表（rewritten_query, reranker_list）→ question_answer_pair_list [[], [], []]：

    • 获取问题。

    • 判断问题 token 的长度。

    • 循环 reranker_list 获取答案 text：

      • 判断 text 的长度。

        • 超长 → 模型压缩 → 调用模型。

      • 装数据 pair。

    • 返回结果。

  4. reranker 模型打分 + 排序：

  5. 动态 TopK 截取数据：

    按分数排好序后，一旦相邻分数出现明显“断崖”（如 0.3 的落差）就提前截断；否则在 min、max 之间按 RERANK_MIN_TOPK / RERANK_MAX_TOPK 取值。

3、output_answer 节点

作用：

把 reranked_docs、context（切片拼接的上下文，回答的参考）+ history（聊天记录）+ item_names + question（重写的问题）交给模型生成答案，同时自己用正则从 context 中提取关联的图片地址。

建议修改提示词顺序：question 向上挪 —— question - context - item_names - history。

参数：

  • 使用：reranked_docs、context（切片拼接上下文，回答的参考）+ history（聊天记录）+ item_names + question（重写的问题）。
  • 生成：answer、image_urls。

步骤（流式 / 非流式）：

特殊情况： 没有识别出 item_name 时，state.answer = xxxxxx，直接返回，不调用模型、不处理图片。

  1. 判断 state 是否有 answer，有就直接返回（state）→ 用 bool 判断有没有 answer：

    • 没有 → return false。
    • 有 → 流式 push_to_session(session_id, delta, {delta: answer})；非流式 return True，state => answer。

  2. 上一次返回的值是 false（即没有 answer），继续往下走。

  3. answer_prompt_text = 声明一个提示词拼接的方法（state）进行拼接。

  4. 调用模型处理字符串 answer 回答的问题（state, answer_prompt_text）：

    state[answer] = ...

  5. 提取图片存储到 state（reranked 里的 text ![]()、mcp 的 url → 判断是不是图片，写入 state）：

    • url → 看后缀名。

    • text → 网络搜索的 markdown ![xxxx](http://xxx)：

    • image_urls → state。

  6. 保存聊天记录（回答）。

  7. 返回 state。
